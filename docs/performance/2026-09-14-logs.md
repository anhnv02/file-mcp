# macOS log performance — 2026-09-14

Measured on Apple M2 / 16 GB. Baseline: `3a555041075a876d4d669f9baf61b7b36443ce8b`; current: working-tree UI changes. Both compiled with `swiftc -O`.

## Method

45 sequential fresh-process trials: 3 repeats × 3 input rates × 5 configurations. Each trial runs for approximately 4 seconds after warm-up. A synthetic ASCII line of 104 characters is supplied through the actual controller append/flush methods. Before timing, log-enabled trials are filled to the existing 500,000-character limit. Actual 150 ms flush scheduling remains enabled. A 10 ms main-run-loop timer generates the workload and measures scheduling delay. Follow-new-logs is on. Hidden/visible refer to the harness window, not navigating tabs in the full app. No settings, credentials, network traffic, or production logs are loaded.

CPU is process CPU time / elapsed time; 100% means one core. RSS is peak resident memory for the entire harness process, including AppKit and warm-up. Disabled trials retain the workload timer but skip log storage/display. Results below are medians of three runs; delay is the median of the per-run maximum delays, not an input-latency percentile.

## Interpretation and limits

At 1,000 lines/s with a full log, the old implementation saturates almost one core and the main-loop timer stalls for 0.76–0.96 seconds in visible-window trials. It processes only 3,470–3,780 of the intended 4,000 lines, despite taking 4.50–4.91 seconds. The new implementation processes all 4,000 lines in approximately 4.01 seconds, uses about 8% of one core, and has maximum scheduling delays of 11–12 ms in the same visible trials.

The old append path repeatedly counts/trims the complete Swift String for each incoming message; the flush path also replaces the complete attributed text. The new implementation bounds the pending NSMutableString and appends only new output. The whole-path measurements support a substantial improvement, but do not isolate how much comes from each change. Flush p95 alone does not improve in all cases; old overloaded runs execute very few timer/flush callbacks, so their small flush timings do not mean a responsive UI.

Hiding the harness window alone does not eliminate log costs. Removing logging entirely saves only roughly 3–4 MiB of peak RSS compared with the new implementation in this harness. Keeping diagnostic logs is reasonable; avoiding hidden-view rendering or reducing routine verbosity could be evaluated next.

Separately, 15 one-second `ps` samples of the currently running FileMCP process (PID 64833) all displayed 0.0% CPU, with RSS 77.84–78.69 MiB. No tunnel-client process was present at the initial process inventory. These sampled, rounded `ps` values are not precise interval CPU measurements. The running binary was not matched to either source version, so this only describes its idle state.

These are short synthetic AppKit tests, not an end-to-end tunnel benchmark, long-duration memory-leak test, or proof of the cause of whole-machine lag. Real log rate, non-ASCII-heavy output, full app tab interactions, GPU/WindowServer costs, and connected runtime workloads were not measured. Sandbox runs emitted an accessibility-services XPC warning; no visual interaction or frame-rate result is claimed. The disabled control also incurs the synthetic 100 Hz timer overhead and is not an estimate of an idle app's CPU usage.

## Reproduce

```sh
python3 tests/benchmark_swift_logs.py --baseline 3a555041075a876d4d669f9baf61b7b36443ce8b
```

Raw trials: `2026-09-14-logs.jsonl`. Live process samples: `2026-09-14-idle.json`. The script writes fresh results under `build/log-benchmark/`.
